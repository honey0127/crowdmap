> 이 문서는 공모전 제출용 기능설명서의 초안입니다. 실제 제출 양식(글자 수 제한, 필수

## 1. 서비스명

**여백(旅白, Yeobaek)** — "여행에 남기는 여백"

## 2. 서비스 개요

과대관광(오버투어리즘)은 특정 명소에 방문객이 시간·공간적으로 몰리면서 발생한다.
여백은 이 문제를 "막기"보다 **"분산시켜서 풀어내는"** 접근을 택한다. 사용자가 가고
싶은 장소들을 담으면, 서울 실시간 도시데이터의 시간대별 혼잡 예측과 한국관광공사
데이터를 근거로 ① 붐빌 시간을 피해 방문 순서를 재배치하고, ② 원래 명소가 여전히
너무 붐빌 경우 **감성이 비슷한 더 한적한 대안("감성 쌍둥이")**으로 자동 치환한
코스를 만들어준다. 관광객 개개인의 동선을 시공간적으로 흩어놓는 것만으로 특정
명소·시간대에 쏠리는 압력을 줄이는 것이 핵심 가설이다.

## 3. 서비스 유형

- 모바일 앱 (Android, Kotlin + Jetpack Compose / View 하이브리드)
- 백엔드: FastAPI(Python) + C++ 네이티브 엔진(pybind11) — 코스 최적화·공간 검색을
  네이티브로 처리해 응답 지연을 낮춘다.

## 4. 상세 기능

### 4.1 핵심 플로우 — 혼잡 회피 코스 플래너
1. **홈 지도**: 구글맵 기반, 명소를 탭해 담거나(＋담기) 지도 위 아무 지점이나 등록(어드혹)
2. **코스 생성**(`/schedule`): 담은 장소들의 방문 순서를 시간의존으로 재배치. 각 장소의
   *도착 예정 시각* 기준 혼잡도를 예보에서 조회해 반영한다(단순 거리순 TSP가 아님).
3. **감성 쌍둥이 치환**(`/match`): 재배치 후에도 특정 장소가 고혼잡(레벨 3 이상)이면,
   임베딩 유사도가 높은 대안 장소를 자동으로 찾아 스왑 후보로 제시.
4. **대안 카드**(`/card`): "왜 이 장소 대신 저 장소인가"를 혼잡도 절감폭·공유 카테고리
   등 **실측 수치 기반**으로 설명(LLM은 문장 표현만 다듬을 뿐 숫자를 만들어내지 않음 — 환각 방지 설계).

### 4.2 신뢰·투명성 — "왜 이 시간?" 근거 화면
장소 상세 화면의 시간대별 혼잡 차트에서 막대를 누르면, 가공된 지수(레벨/한적함 점수)
뿐 아니라 **원본 API 값**(서울시 실시간 도시데이터의 예측 인구 범위, 원문 레벨 라벨,
출처 문구)을 그대로 노출한다. "왜 이 시간이 좋다는 건지" 사용자가 직접 원본 데이터로
검증할 수 있게 하는 장치 — 데이터 활용의 신뢰성을 사용자 UX 레벨까지 끌어올린 부분.

### 4.3 여백 지수 (0~100)
한 코스의 "혼잡 회피 품질"을 혼잡도·감성 유사도 보존율·이동 효율 세 지표를 가중합산해
단일 숫자로 표현. 스토어 스크린샷·시연에서 설명 없이도 "이 코스가 얼마나 잘 짜였는지"를
직관적으로 전달하기 위한 브랜드 지표.

### 4.4 데이터 소스 다각화 — 서울(시간별) + 전국(일별) 이중 트랙
- 서울: 실시간 도시데이터(`FCST_PPLTN`)로 **시간 단위** 혼잡 예보.
- 전국: 한국관광공사 관광지 집중률 예측(`TatsCnctrRateService`)으로 **날짜 단위**
  혼잡도 — 서울 예보권 밖 지역까지 커버.
- **D+1 역사 평균 폴백**: 서울 API의 예보 창(~12시간)을 벗어난 조회("내일 여행" 시나리오)는
  기존엔 무조건 중립값이었다. 이제 서버가 실측 예보를 누적 저장해두고, 예보 창 밖 요청은
  같은 지점·같은 시간대의 **과거 관측 평균**으로 대체한다. 표본이 쌓일수록 정확도가
  올라가는 구조 — 서비스 발전성(사용할수록 좋아지는 설계) 근거.

### 4.5 안정성 — 서버 무중단 설계
- **엔진 폴백**: 코스 최적화는 C++ 네이티브 엔진이 담당하지만, 배포 환경 문제 등으로
  엔진이 없어도 순수 파이썬 스케줄러가 동일한 비용함수·로직으로 대신 계산해 서비스가
  절대 완전히 죽지 않는다(`/schedule` 503 제거).
- **로컬 캐시 오프라인 폴백**: 마지막으로 성공한 코스를 기기에 저장해두고, 서버 응답
  실패 시 자동으로 보여준다("오프라인" 배너 표시) — 네트워크 문제로 화면이 완전히
  비는 상황을 방지.

### 4.6 그 외 기능
- **지역구 플래너**: 성수·홍대·강남 등 지역구 단위로 명소 라인업을 받아 코스 생성
- **미시적 분산**: 특정 명소 주변 도보권(~0.9km)에서 더 한적한 대안 추천
- **오프피크 추천**: 향후 12시간 중 가장 한적한 시간대 top3
- **실시간 급증 감지 + 리스케줄**: 코스 진행 중 다음 방문지가 갑자기 붐비면 알림
- **크라우드소싱 제보**: 여행자가 직접 "지금 붐빔/한적함/팁"을 등록·조회
- **에코 리워드 + 여백 스탬프**: 한적한 선택에 포인트를, 방문(담은) 장소마다 로컬
  스탬프를 적립 — 서버 없이도 동작하는 리텐션 장치
- **일정 카드 이미지 공유**: 대안 카드를 이미지로 캡처해 SNS 등에 공유
- **다국어**: 온보딩 화면 영어 로케일 지원(외국인 관광객 = 오버투어리즘의 실질 주체라는
  기획 논리와 연결)

## 5. 활용 API (데이터 활용 20점)

| API | 제공처 | 호출 방식 | 용도 |
| --- | --- | --- | --- |
| TourAPI(KorService2) | 한국관광공사 | **런타임 수집·주기 갱신**(`scripts/collect_tourapi.py`가 OpenAPI를 HTTP로 호출해 SQLite에 적재 — 정적 파일 다운로드 아님) | 전국 관광지 기본정보·좌표·소개글 |
| 서울 실시간 도시데이터(`citydata_ppltn`) | 서울열린데이터광장 | **요청마다 실시간 HTTP 호출** | 시간대별 혼잡 예보(`FCST_PPLTN`) — 코스 재배치·오프피크·근거 화면의 원천 |
| 관광지 집중률 예측(`TatsCnctrRateService`) | 한국관광공사 | **요청마다 실시간 HTTP 호출** | 전국(서울 밖 포함) 날짜 단위 혼잡도 — 지역구 라인업 반영 |
| 관광지 별 연관 관광지 정보(관광 빅데이터) | 한국관광공사 | **요청마다 실시간 HTTP 호출**(결과 캐시) | **감성 쌍둥이(대안 추천)의 공식 근거** — '이 곳을 찾은 사람들이 함께 찾은 곳'을 자체 임베딩 유사도와 결합해 재정렬 |

> ⚠️ TourAPI는 사전 수집 방식이라, 제출 문서에는 "OpenAPI로 수집·주기 갱신"임을
> 명시해 "단순 파일 다운로드"와 구분되게 서술할 것 — 실시간 도시데이터·집중률·연관
> 관광지 API는 요청 시점마다 직접 호출하므로 이 이슈에서 자유롭다.

### 대안 추천의 근거 결합 (연관 관광지)

```
후보 점수 = 1.0 × e5 임베딩 유사도(자체 계산)  +  0.6 × 공사 연관 관광지 순위 보정
```

- 응답에 `related_rank`(공사 연관 목록 순위)와 `basis`(`both`/`embedding`/`related`)를
  실어 **왜 이 대안인지**를 앱에서 그대로 보여준다("관광공사 연관 관광지 2위" 등).
- 연관 API가 없거나(키 미설정·쿼터 초과) 장애일 때는 임베딩만으로, 임베딩 벡터가 없을
  때는 연관도만으로 동작한다 — 어느 쪽이 빠져도 기능이 멎지 않는다.
- 일일 트래픽(개발계정 1,000건) 보호: 장소명 단위 캐시 + 연속 실패 시 서킷 브레이커
  (5분 차단)로 불필요한 재호출을 막는다. 상태는 `/health`의 `related`에서 확인.

### ⚠️ 데이터 동기화 계획 (공사 요청사항)

공사 안내에 따르면 **관광정보를 서버에 저장해 서비스하는 경우 동기화 계획을 요청**하며,
이행되지 않으면 서비스가 차단될 수 있다. 여백의 계획:

| 대상 | 주기 | 방법 |
| --- | --- | --- |
| TourAPI 장소 기본정보 | **월 1회** | `scripts/collect_tourapi.py --nationwide` 재실행 후 재배포 |
| 예보지점 매핑 | 장소 갱신 시 | `scripts/build_area_map.py` |
| 집중률·연관 관광지·실시간 혼잡 | **저장 안 함** | 요청 시점 호출 + 단기 메모리 캐시만 사용 |

원천 데이터(제목·주소·좌표·개요)는 **변형 없이 그대로** 저장하며, `quiet_score`·혼잡
레벨 등은 원천을 수정한 것이 아니라 별도로 계산한 파생 지표다.

## 6. 기술 스택

- **클라이언트**: Android(Kotlin), Jetpack Compose + 기존 View 화면 병행, Retrofit2+Gson, Google Maps SDK
- **서버**: FastAPI(Python), SQLite, numpy(임베딩 유사도), multilingual-e5-small(문장 임베딩)
- **엔진**: C++17 + pybind11 — 공간 반경 검색, 시간의존 코스 최적화(완전탐색/2-opt)
- **배포**: Docker(멀티스테이지 — 컨테이너 안에서 C++ 엔진까지 직접 빌드), Fly.io

## 7. 차별점 · 독창성 (서비스 기획력 30점)

- 오버투어리즘 대응을 "규제/차단"이 아니라 **"같은 만족도를 주는 대안으로의 자연스러운
  분산"**으로 접근 — 임베딩 기반 "감성 쌍둥이"가 그 핵심 장치.
- 혼잡도를 코스 최적화의 **입력 변수**로 다루는 시간의존 스케줄러(단순 최단거리 TSP가
  아니라, 방문 순서에 따라 각 지점의 도착 시각·그 시각의 예측 혼잡도가 달라지는
  문제로 정식화) — 부록 C 비용함수 참고.
- 데이터의 "신뢰성"을 사용자에게 직접 노출(왜 이 시간? 근거 화면)해, 추천이 블랙박스가
  아님을 증명하는 UX 설계.

## 8. 발전 로드맵 (서비스 발전성 20점)

### 이미 구현: MCP 서버 — 여백을 AI 에이전트의 도구로 개방

여백은 앱으로만 쓰이지 않는다. **MCP(Model Context Protocol) 서버**를 함께 제공해
Claude·ChatGPT 같은 AI 에이전트가 여백의 혼잡 회피 엔진을 직접 호출할 수 있다.

```
사용자 → AI 에이전트 → (MCP) → 여백 엔진 → 혼잡 예보·감성 쌍둥이·코스 재배치
```

| 도구 | 하는 일 |
| --- | --- |
| `find_quiet_alternative` | 붐비는 곳 → 비슷한 분위기의 한적한 대안 |
| `plan_quiet_course` | 장소 목록 → 혼잡 회피 하루 코스 |
| `get_offpeak_hours` | 덜 붐비는 시간대(예측 인구 근거 포함) |
| `get_congestion` / `search_places` | 현재 혼잡도 / 장소 검색 |

- 엔드포인트: `POST /mcp` (앱 API 와 동일 서버, JSON-RPC 2.0)
- 도구 구현은 앱이 쓰는 라우트 핸들러를 그대로 호출 → 앱과 AI 의 답이 항상 일치
- 의미: 서비스가 **재사용 가능한 관광 혼잡 회피 엔진**으로 확장된다.
  타 여행 서비스·챗봇이 여백을 가져다 쓰는 B2B 경로가 열린다.
- 상세: `MCP.md`

### 그 밖의 계획

- **단기**: 서울 지하철 실시간 혼잡도(OA-12928) 연동으로 이동 구간까지 분산 반영,
  집중률 캐시 테이블화로 API 호출 비용 절감
- **중기**: 대중교통 혼잡 반영 길찾기("덜 붐비는 경로"), 예약 타임슬롯 통합, 실제
  쿠폰/상점 제휴로 에코 리워드를 현금성 혜택으로 확장
- **장기**: 크라우드소싱 제보 신뢰도 모델링(신고·사진 첨부), 탄소발자국·지역소득 분산
  시각화, D+1 역사 평균의 정확도를 표본 축적에 따라 지속 개선(사용자가 늘수록
  서비스 품질이 함께 올라가는 구조)
